# Tags to organize tasks, and Inbox and Backlog stages

Tasks pile up: CodeAlta has 29, stride 32. Work items sorts them by stage, kind and date, and finds them by text, but nothing groups them by topic. This plan gives each project a short list of **tags** the user owns, with a description each, and puts them on tasks. Agents apply existing tags to the tasks they create, and may propose a new tag, but only the user creates, renames or deletes one. The stages get names that say what they are: **To do** is where a new proposal waits for a decision (an inbox), and **Later** is where a task the user keeps waits (a backlog).

## Decisions taken

- Tags belong to the user. Agents apply existing tags to new tasks, and propose new tags, never create them.
- A tag created in Work items can be applied to the existing tasks it fits, found by a session and checked by the user before anything is written.
- Tags are stored with the task, in its front matter; the list of tags of a project is a file of the project.
- No priority for now. If the user makes a tag such as `next` or `urgent`, priority can become a field with its own sort later; it would then be the user's, also on the proposal card.
- No **Keep** button on the proposal card: an open card is the task still waiting in the Inbox, and **Backlog** is the decision to keep it.
- **To do** becomes **Inbox**, **Later** becomes **Backlog**. **Inbox** rather than **New**, because the stage also holds the plans and the reviews that wait for the user, which are not new.

## What changes

### Inbox and Backlog

Only what the user reads changes. The statuses in the files stay `pending` and `later`, and `alta task` keeps its commands and statuses, so nothing is migrated and agents are not affected.

| Today | After |
| --- | --- |
| Tabs **To do**, **In progress**, **Later**, **Closed** | **Inbox**, **In progress**, **Backlog**, **Closed** |
| Status tag **To do** of a task, **Later** | **Inbox**, **Backlog** |
| **Later** on a task's card and in its detail ("Keep the task for later") | **Backlog** ("Keep the task in the Backlog of Work items") |
| **Back to To do** | **Back to Inbox** |
| **Later** on a plan's card (puts the card away) | Unchanged |

Where: `workStatusLabel`, `workFilterLabel` in `workItems.ts`; the buttons in `WorkItemCards.tsx` and `WorkItemsPanel.tsx`; `localization.ts` (five languages each); `site/docs/work-items.md`. Notifications and the Explorer counts say "wait", not the stage name: check them, change nothing else.

### The tags of a project

A file of the project, beside the tasks, shared through git like them:

```yaml
# .alta/tags.yaml
tags:
  mobile: The phone app and the Mobile server of the desktop.
  flaky-tests: A test that fails at random, or only on some machines.
  claude-code: The Claude Code provider and its CLI.
declined: [ci-noise]
```

- A name is lower case letters, digits and hyphens, 32 characters at most; a description is one line, 200 characters at most, and optional. The description is what agents match a task against: the tag manager asks for one.
- `declined` lists the names the user turned down when an agent proposed them, so that no session proposes them again.
- A tag's color comes from its name (a hash into a fixed palette that reads on both themes): there is nothing to choose.
- A tag found on a task but missing from the file (written by hand, or from another branch) is shown as any tag, and the tag manager lists it with **Describe** to add it to the file.

Catalog: `WorkItemFiles` reads and writes the file (SharpYaml, as the other YAML of the catalog), `WorkItemService` exposes the tags with how many open tasks have each, and renames or deletes a tag in the file and in every task that has it.

### Tags on a task

```yaml
---
title: "Fix the Notes overlays browser test whose docking menu stays open"
kind: problem
status: later
created: 2026-11-09
tags: [flaky-tests]
summary: "..."
---
```

`WorkTask` gets `Tags`; `SerializeTask` writes the line only when there are tags; a new `WithTags` changes that line alone, as `WithStatus` does for the status. `PromptFileFormat.SplitFrontmatter` already reads block lists; the inline `[a, b]` form is checked, and read too if it is not.

### In Work items

- **Rows** show their tags as small chips after the date, at most three, then `+2`.
- **Detail**: a tag field under the title. Typing completes from the project's tags; **New tag "x"…** opens the small dialog of a new tag (name, description).
- **Filter**: a **Tags** menu beside the kind filter lists the tags of the project with their counts, and keeps the tasks that have any of the ticked ones. Typing `#mobile` in the search box does the same.
- **Card and Details window** of a proposal: the tags the agent applied, as chips; they are changed in the detail.
- **Tag manager**, in the settings of Work items, per project: each tag with its description and count, **Rename**, **Delete** (both rewrite the tasks that have it, after a confirmation that says how many), the tags missing from the file with **Describe**, and the declined names with **Forget**.

### A new tag finds its tasks

When the user creates a tag (in the detail or the manager), the dialog offers **Find the tasks it fits**, ticked by default.

1. CodeAlta starts a session in the project, titled "Tasks for the tag mobile", on the quick tier when Settings > Models sets one, otherwise on the default model with low reasoning. It is told to read the open tasks (`alta task list`, then the ones whose title and summary are not enough), change nothing, and answer with `alta tag matches mobile --tasks <short ids> --stdin` (one line of reason per task on stdin).
2. That command records the matches for the user; the session ends.
3. Work items shows **3 tasks fit the tag mobile**, with **Review**: a dialog lists them ticked, each with its title and the reason; **Apply** writes the tag to the ticked ones.

The session is an ordinary session the user can open, follow or stop. Nothing is written to a task before **Apply**.

### Agents apply tags to the tasks they create

- `alta task create --tag <name>` (repeatable) accepts only the project's tags; an unknown one is refused with the list of the tags. `alta tag list` prints the tags with their descriptions and counts.
- `alta task list` prints the tags of each task and takes `--tag <name>`.
- `alta task tag <id> --add <name> --remove <name>`, for when the user asks an agent to tag tasks.
- The Follow-up tasks section of `default.prompt.md` (and its copies in the other agent prompts that propose tasks) says: before creating a task, read `alta tag list` and add the tags whose description fits; when none fits, add none.

### Agents propose a tag

- `alta tag propose --name <name> --description <text> --tasks <short ids>` records a proposal for the user; it creates no tag. It is refused for an existing or declined name, with fewer than three tasks (the new task counts), or when the session already proposed a tag in the current turn.
- The prompt says when: no existing tag fits the task just created, and at least two other open tasks share its topic.
- The proposing session's card shows the proposal after its tasks: **Suggested tag `flaky-tests`**, its description, **fits 3 open tasks**. **Create** opens the dialog of a new tag, filled in, with the tasks ticked as in **Review** above; **Dismiss** adds the name to `declined`.
- A proposal is kept with the other links of the session (as `WorkItemLink` is), not in a file: it is not a tag until the user creates it.

## Out of scope

- Priority (see the decisions).
- Tags on plans and reviews: few of them, and they are short-lived.
- The TUI: no tag screen (desktop only, AGENTS.md). The `alta` commands are shared, so the TUI's agents use them too; the TUI shows Inbox and Backlog only if its labels come from the same place, and is checked to build and pass its tests.
