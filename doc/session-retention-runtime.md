# Automatic retention runtime contract

The retention runtime is a **host-composed, fail-closed startup operation**. Constructing the runtime service does not start cleanup. `SessionRetentionService.RunOnceAsync` starts or joins one original pass; `Subscribe(Action<SessionRetentionStatus>)` immediately replays the immutable current status, publishes ordered changes, and returns a disposable subscription. Callbacks must not block; callback failures cannot fail retention. The host supplies one captured UTC time and a validated UTC cutoff from Catalog's storage policy; a null cutoff means Never. The host owns cancellation and must join the worker before releasing runtime/archive dependencies. Settings or window cancellation must not release a running retirement.

`DesktopSessionRetention` is composed after owned host/plugin startup, borrows `RetirementArchive` from the active built-in Statistics plugin, reads the global policy, waits for initial protection readiness and starts the original pass. It cancels/joins that pass before host disposal. External composition is qualified only after RPC/LiveTool/reminder producers have been installed with the original registry; desktop restoration is independent. A missing owner reports a skipped pass, never readiness inferred from empty public work lists. Disabled or missing Statistics does not skip the pass: saving Statistics is best effort. Never reports `disabled`. Exact-handle deletion currently supports qualified local Windows storage only.

`storage.watchRetention` is an epoch-checked, bounded latest-value stream of that same service's status: state, examined/deleted/skipped session counts, and reason. It replays the current outcome to late windows and never starts or retries maintenance. Disposing the subscription only ends observation. The separate scratchpad stream retains decimal-string Int64 file counts; retention's Int32 session counts are JSON numbers. App-owned subscriptions outlive the Storage page and use one toast key per operation, so scan cancellation or Settings navigation cannot cancel either host operation. A broken status stream or host-liveness outage leaves known terminal outcomes intact for the same host epoch; unfinished work becomes unavailable, not completed. Only a change of host identity clears the prior outcomes.

## Readiness is authorization, not observation

`SessionRetentionProtection` initially protects everything. The host must name every participant with `SealParticipants`, then publish complete, ready sets for all desktop windows/spaces (including inactive-space open tabs and drafts) and external work owners. A missing or unknown participant prevents retirement.

Before opening a tab, creating/editing a draft, scheduling a reminder/delivery or changing lineage, its owner must **claim the affected IDs before making the operation visible or runnable**. `Publish` atomically replaces one participant's complete ID set; a false return means retirement already owns an ID and the operation must not proceed. A disconnected/unknown participant calls `MarkUnknown`, retaining its protected IDs. An observational snapshot after opening is not this handshake. Do not mark a participant ready until every route is integrated; leave retention skipped instead.

The host creates one `SessionRetentionProtection` before provider/plugin startup and supplies that same object as `ISessionRetentionAdmission` to Hub, model preparation, plugin tasks/UI, LiveTool and reminders. Known targets use overlapping reference-counted session claims; genuinely unknown targets temporarily protect all sessions. The original provider refresh—not a canceled `GetModelsAsync` waiter—owns its preparation claim. Model initialization retains the original outcomes and joins them before host shutdown releases providers; a presentation layer catching an error cannot discard retained dependencies or turn that drainage into success. Completed retirement IDs remain tombstoned for that host lifetime, preventing stale explicit-ID resurrection. Direct resume also rejects missing owned journals before provider construction. Hub attachment claims survive references, provider/event callbacks, unsubscribe and session/provider disposal. Raw provider adapters transfer executor ownership to `AgentRuntime`; wrappers must not own separate hidden session work.

Ownership decisions inspect the **complete original task outcome**, including sibling faults in `Task.Exception`, not merely the first exception thrown by `await`. A dependency-retention marker means release is unconfirmed: claims stay held even though an observer has received an error. Transfers must overlap; a timeout, canceled observer or transport failure is never downstream admission. Startup waits up to 30 seconds for the registry's first complete restoration before launching its single pass; an owner still unknown makes the pass skip. Deletion rechecks current readiness under the registry lock. Shutdown cancels that readiness wait or joins the already-started original worker. Neither later readiness, reconnect nor a settings edit retries cleanup.

The production model registry also pins each cached runtime during its original preparation. Live provider replacement/removal refuses a pinned registration before changing it; saving configuration can therefore report that applying it failed while preparation is active. A retained-dependency result keeps the actual runtime, original task, timeout source and both claims alive. Registry shutdown closes preparation admission atomically and disposes nothing while any pin remains. The published refresh precedes pin acquisition, and registry locks are never taken under initialization's state gate; this lets drainage see a preparation even while its registry acquisition is blocked or a factory reenters. Custom registry implementations own their equivalent mutation/disposal synchronization.

The command owner uses the existing deletion reservation, rejecting competing owned send/queue/steer/compact/remote operations. Retirement holds the candidate actor mailbox through archive and deletion; canceling shutdown is delivered to the body without canceling the original actor reply wait and prematurely releasing claims. Direct runtime queue/send/resume, notes/events/session-state mutation and parent/provenance publication share admission claims; a successful retirement keeps a runtime tombstone, and queue execution rechecks the journal generation. Family lineage is read from the session list the pass already has (parent, creator and view parent of each session): an expired session is retired only once no remaining session names it, so a recent child keeps its whole family and an expired family is removed leaves first in the same pass. Every attached runtime entry, pending permission/input, job (including completed jobs awaiting delivery) and remote request is protected. Jobs have a separate atomic admission reservation, normalized session IDs and pending-delivery ownership independent of their bounded presentation history.

The native host registers each session-capable window unknown before exposing its bridge and binds its `sessionRetention` service through host-owned callbacks, never a renderer-supplied owner. The current owned desktop has one such window and refuses popups. `sessionRetention.publish` is epoch/page/revision fenced and requires the matching host-authenticated document lifetime watch. The frontend consumes the watch's first item before restoring readiness, then keeps it open. Effective channel cancellation revokes readiness; native navigation/reload, process failure and shutdown also invalidate the page. Session-owned resource disposal alone is too late because RPC teardown may first wait for unrelated channels. A replacement page cannot clear the permanent unknown latch for this pass.

The service retains the union of admitted all-space open/draft IDs, including inactive and orphaned spaces; closing a tab or disconnecting a page never releases that protection. Malformed or oversized publications are refused. Initial restoration, subsequent navigation and draft/composer work require acknowledged protection before becoming visible or runnable; an effect-only inventory is not a deletion grant. Plugin prompt handoff remains owned until definite downstream acceptance or conclusive refusal/cancellation. Unknown Close messages and lost responses do not acknowledge cancellation, and published requests are not replayed after reconnect.

External-work coverage includes the **original** lifetimes of reminder creation/firing (including firing captured before removal), LiveTool preparation before session resolution, captured parent notifications, plugin RPC commands and pending prompt handoffs, direct `AgentHub` start/resume before provider construction through disposal, and unscoped plugin tasks with no known target. Direct runtime steer/compact/history, host prompts and skill preparation also retain their claims before actor/provider preparation. Automations/work items that create a new session do not themselves schedule work on an old target. Only explicit `SessionRetentionIndependent` tasks may opt out; the built-in Statistics history/flow readers use this non-session contract and tolerate concurrent retirement. A host borrowing a plugin runtime requires completed original startup and the same admission registry identity; an unknown or mismatched runtime remains a separate unknown participant.

## Journal age and Saved Statistics

Age is the last write time of the journal file, never `UpdatedAt` or a Statistics inspection timestamp. Every write to a session appends to its journal, so its last write time is its last activity. The pass reads it with a file stat, and retirement reads it again from the held handle; the journal is never parsed to decide its age, so no record format, unknown record, damaged tail or old journal without a CodeAlta header can keep an expired session. Exactly-on-cutoff sessions remain. A first implementation parsed each journal with a closed list of record types: every real journal held an unlisted type and was kept.

`CodeAlta.Agent.ISessionStatisticsRetirementArchive` is the optional capability of the existing active Statistics engine, not a second engine or receipt system:

1. `PrepareAsync(sessionId)` serializes with history/reset/forget and **never reads the journal**. When Statistics has read the session to the end of its current file (same length and write time, current facts version, no history floor), it durably writes the facts its tables hold as an immutable archive generation and returns a receipt; otherwise it returns a reason and saves nothing. The source of the receipt is described by its path, length and write time, with no digest. The runtime gives it 60 seconds; after a timeout the pass stops asking it.
2. The runtime keeps a receipt only when its session ID, canonical journal path, length and write time match the held source, and then only to reconcile it.
3. `ReconcileDeletedAsync` is idempotent and records confirmed removal/partial artifacts. The archive participant also owns restart rehydration and missing-source reconciliation after a crash. It must never sweep saved artifact paths during reconciliation.

Saving is best effort: no participant, disabled/limited/unread Statistics, a refusal, a bad receipt, an archive exception or no answer in time never keeps an expired session. The facts Statistics has already read survive the deletion of their journal; the saved copy only adds survival across a Statistics reset, so a session deleted without one loses its numbers only at a reset. An earlier design re-read and hashed every expired journal while holding it: on a large profile that took longer than the timeout, and old sessions were never deleted. Runtime unit tests use a fake archive to prove ordering and that failures still delete. `SessionRetentionArchiveIntegrationTests` additionally uses the real Statistics engine and Windows native lease on synthetic data: it observes committed archive bytes before deletion, verifies writer exclusion and the host reservation, and compares complete projections through repeated reset/reopen without duplicate generations. Disabled/locked archive fixtures still delete the source and artifacts. Producer lifetime tests and desktop restoration/transport tests separately cover admission; archive equivalence alone is never a substitute for production-owner qualification.

## Exact-source filesystem boundary

On Windows, retirement opens each ancestor without following reparse points using `FILE_LIST_DIRECTORY | FILE_READ_ATTRIBUTES` (attributes alone are insufficient for share arbitration), pins them against replacement/reparse-tag writers, and opens the ordinary single-link journal with read/delete access while denying writes and replacement. Construction-window adversarial tests try an existing directory writer, new reparse-capable directory writers and renames immediately after each ancestor is claimed, **before** the descendant is opened. It reads the write time from the file handle, without reading the content, and keeps the handle through the Statistics save. Archive readers must share delete access (`FileShare.ReadWrite | FileShare.Delete`). Removal sets disposition on the **same verified handle**; it never unlocks then deletes by path. A protection-readiness loss is serialized against that final disposition. Unix currently reports `platform_unsupported`; there is no weaker path-based fallback.

Before deletion, the same operation captures at most 256 ordinary, exclusively held files immediately under the owning `<id>.attachments` directory plus the owning layout's trace. Nested directories, links, hardlinks, inaccessible/locked artifacts and excess entries stay untouched and produce a partial result. No transcript-supplied path is used. Empty attachment/date directories may remain: avoiding stale-path directory removal is preferable to reclaiming a few empty folders. Artifacts are never retried after their source disappears, so a later file at a reused path is not a cleanup target.

After closing delete-pending handles, the runtime removes/invalidate catalog projections, notifies the session catalog and reconciles the durable receipt. Failures are reported as pending/unconfirmed, not false success. No project, working directory, configuration, credential, database/archive, unknown entry, peer profile or sessions/date root is recursively removed.
